# 板载 RTC 接入（2026-11-06）

RTC 驱动已接入完整屏幕应用。启动先读硬件时间，原厂 `+sntp:<UTC秒>`
和协商后的 `SC_MSG_CLOCK` 共用授时入口；只有接受新的 ESP32 时间才安排写回。
显示时区仍使用 ESP32 下发的分钟偏移。RTC 缺失、掉电标志、停振模式、无效日历
或 I²C 故障不会阻止显示、传感器和串口服务启动；没有有效时间时不伪造时钟。

## 原厂依据

分析镜像为 `SENSOR3_MCU-SV.04.00.04.00.bin`，SHA-256：
`1d0b848af6195b39849260a3c9ff2a020d574ca9b98c2c2665d2278f349796c2`。

| 项目 | 证据与实现 |
| --- | --- |
| 初始化 | `0x1a110`，原厂主程序 `0x43920` 调用 |
| 引脚 | PD2 为 SCL，PC7 为 SDA；软件 I²C |
| 地址 | 7 位 `0x51`，线上写 `0xa2`、读 `0xa3` |
| 读时 | `0x1a14c` 从 `0x02` 连读 7 字节：秒、分、时、日、星期、月/世纪、年 |
| 写时 | `0x1a224` 从 `0x02` 连写 7 字节，BCD 日历 |
| 存储时区 | 原厂 SNTP 分支 `0x4def4` 将 Unix 时间加 `0x7080`（28800 秒），经 `0x14f2c` 转日历，在 `0x4dfba` 调用 RTC 写入 |

这是 **PCF8563 兼容寄存器布局**，尚未通过芯片丝印确认具体厂商/型号。
寄存器约定依据 [NXP PCF8563 PDF](https://www.nxp.com/docs/en/data-sheet/PCF8563.pdf)。
原厂世纪位为 0 时按 20xx 解释，社区沿用；不因 UI 时区更改而改变 RTC 存储时区。

## 行为和边界

- 接收时间以 UTC 秒计，RTC 存固定 UTC+8 日历。支持现有串口协议的最早时间
  `1700000000` 至 `2099-12-31 23:59:59 UTC+8`，校验 BCD、闰日、月末和星期范围。
- 启动只读取控制寄存器和日历，遇到 VL、STOP、测试模式或无效日期时拒绝作为时源。
  不在启动时写默认日期，也不盲目复位 RTC。
- 接受 ESP32 授时后，先读 RTC；误差不超过 1 秒时免写。否则连续写 7 字节日历，
  必要时恢复 control/status 1 为正常模式，然后读回校验。最多尝试 3 次，间隔 1 秒；
  重试使用当前推进后的时间，不重复写旧秒值。
- control/status 2、闹钟、CLKOUT 和定时器寄存器保持原值。板级写入口只允许完整
  日历写入或正常模式恢复，拒绝闹钟等寄存器写入。
- 所有时源进入同一软件时钟；每轮按完整秒推进并保留毫秒余数，支持 32 位毫秒计数
  回绕。原厂 JSON 应答时间戳也取这个时钟。
- 每 60 秒尝试读取 RTC 校正离线走时；ESP32 在最近 120 秒内授时则跳过。
  如果网络授时写回失败，不允许旧 RTC 覆盖已经接受的网络时间，继续软件走时。
- 总线使用开漏和上拉，先在输入模式建立开漏再开启输出，避免初始化时短暂推挽拉高。
  SCL 等待有固定次数上限；SDA 卡低最多尝试 9 个恢复时钟。所有失败路径释放引脚。
  I²C 过程中不关中断、不依赖 SysTick 等待，也不在等待循环喂狗。
- RTC 初始化位于 **30 秒内部 SRAM 串口维护窗口之后**。最小维护固件不启动 RTC；
  OTA 二进制收发期间不轮询或写 RTC。原厂升级、引导区导出和恢复门控保持原实现。

## 验证与实机验收

`tests/rtc.c` 检查 UTC+8 固定向量、跨日/跨年/闰日、无效日历和电压标志、读写错误、
写后校验、免写、三次重试、计数回绕、两种 UART 授时入口及无协商/重放拒绝。
`tests/rtc_bus.c` 运行真实板级总线代码，以独立 I²C 从机模型检查地址、重复 START、
最后一个字节 NACK、各位置 NACK、SCL/SDA 卡低、9 时钟恢复和引脚隔离。
主机用例及 ASan/UBSan 检查不代替物理总线测量。

完整和最小维护 ARM 镜像均需构建；实际 ARM 指令检查需确认未映射 SDRAM 时仍能启动
维护服务和导出引导字节，真实引导 scatter 初始化不会清除恢复锁存。
构建、校验值与当前测试结果保存在 `artifacts/rtc-20261106/`。

早先访问 Mac SSH 与旧 ESP32 HTTP 地址不可达，首次 RTC 构建没有刷入。
随后连接设备新管理页，已将包含恢复锁存修复的 RTC 镜像通过 UART OTA 安装，
内部 Flash MD5 匹配。但是业务启动后 ESP32 记录欠压复位，MCU 再次进入强制维护，
传感器和 RTC 实机验收未通过。见 [本次排查记录](MCU-RECOVERY-20261106.md)。
修复版产物保存在 `artifacts/rtc-20261106-recovery-fix/`，原始 RTC 构建继续留档。
后续应先排查供电和 MCU 故障，再核验：

1. 安装前获取当前会话的双遍引导备份，按原有门控暂存、校验并安装。
2. 授时后确认显示及翻页正常；再让 ESP32 暂不授时，仅复位 MCU，观察 RTC 恢复时间。
3. 恢复 ESP32 授时，确认时区切换只改变显示；跨分钟观察走时。
4. 复核串口维护与 OTA 可用；断电保时能力需根据 RTC 实际供电/后备电路验证。

尚未测量实际 RTC ACK、振荡器精度、供电保持时间或物理总线波形；不据软件测试
推断具体 RTC 芯片型号、误差或整机断电后必然保时。
