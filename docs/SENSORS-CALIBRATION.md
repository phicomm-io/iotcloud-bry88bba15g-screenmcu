# 原厂温湿度补偿与校准实现

2026-11-05。目标 SWM34SVET6-50；依据 SENSOR3_MCU SV.04.00.04.00，SHA256 `1d0b848af6195b39849260a3c9ff2a020d574ca9b98c2c2665d2278f349796c2`。当前完成可移植 C 核心、runtime 接口和离线 CPU 对照；尚未接上板级 I²C/UART/Flash 配置读取，也未生成可烧写映像。

## 实物按键对应

用户已确认：**PD11 是正面用户触摸按键；PD13 是硬件背面孔内独立按钮**。两者均低有效 GPIO 轮询事件。不能把 PD11 当成带坐标的触摸屏，也不能要求用户点击屏幕任意区域。PD11 的首次只唤醒、松开切页、长按和启动门控需要 BSP 后续接入；浏览器双击导航只是社区预览交互，未证明原厂支持双击。

## 温湿度

`src/sht_compensation.c` 对应原厂 `0x18268..0x18e04`。配置映射：

| C 字段 | 原厂 config 偏移 | 类型 |
|---|---|---|
| temperature | +4 | int16，十分位补偿量 |
| secondary | +6 | int16，第二补偿量，实际板级用途不臆测 |
| hcho_heat | +8 | int16，HCHO 状态关联的补偿量 |
| humidity | +10 | int16，湿度偏移，仅原厂简化分支使用 |

必须从校验后的实际板级配置加载，不能用假定的出厂系数。调用 `screen_runtime_sensor_config()` 后，`screen_runtime_sht()` 才接收样本并更新显示模型；温湿度最终值为原厂十分位整数/10。校验失败不推进补偿状态，不覆盖旧样本；旧样本仍受既有有效期约束。

- CRC8 初始 0xff、多项式 0x31；CRC 或 I²C 失败不能推进样本数。
- 原始温度 `float32(175*rawT/65534 - 45)`，原始湿度单精度 `100*rawRH/65534`；保留原厂 double/float 舍入点。
- 时间基准是**成功样本数 ×2.06**，不是系统运行秒数。大于 4200 置 settled（保持置位）；渐变模式下 `<=480` 清零两个补偿状态。
- 基础目标 `temperature+secondary`，步长为目标/3720×2.06；HCHO 关联步长为 hcho_heat/480×2.06。状态 0x59 时按原厂逻辑回归零，其余状态趋近 hcho_heat。方向比较基于绝对值，不能改成通用线性插值。
- 最终温度从原始十分位整数加两个 double 补偿后向零截断，显示限制到 -200..600。湿度重算使用**未限幅的补偿温度**，不能用显示温度代替。
- temperature 配置为 0 时，湿度为原始十分位整数+humidity，限 0..999。否则走湿度重算；此分支不再加 humidity。

湿度重算的饱和压多项式：

```
P(T) = 0.0007*T^4 + 0.0086*T^3 + 1.8046*T^2 + 41.449*T + 616.58
mix = (float32(float32(RH*622)/100) * P(rawT))
      / (10132500 - float32(RH/100)*P(rawT))
RH10 = trunc(1000 * mix*10132500 / (P(correctedT)*(mix+622)))
```

mix 为 0 时输出 0，最终限 0..999；correctedT 为未限幅十分位温度/10 后的 float32。公式说明不能替代 C 中的求值顺序。编译关闭浮点乘加合并，不能启用 fast-math。原厂恰好发生步长越界、计数回绕等行为均在正常路径保留。

`src/sensors.c` 同时修正原始湿度分母为 65534，并增加 HCHO CMD=1 最终换算及 frame[13] 原始状态读取。最低长度、LEN 和 checksum 不通过均不修改输出。未把未知的 HCHO 线上整数直接命名为 mg/m³。

## CO₂ / TVOC 校准

原厂执行器 `0x4431c` / `0x44768` 已恢复至 `src/calibration.c`。**正常的 service/calibration 可以设置请求位并启动执行器。** 上一轮把 `lsls #29` 后的 `cbz` 误解为只测试 bit2；实际测试的是低三位是否全零。实现以原厂机器码执行结果为准。

`calibration_factory_service()` 接收已校验的 co2/tvoc 参数；两个字段均必填，值 1 添加对应请求位，其他值保留已存在的请求位。正常返回表示请求已接收，不能表示物理校准成功。runtime 的 `screen_runtime_calibration_service()` 将它接到同一个执行器。原有 UART owner 仍负责 JSON/client_token 校验及应答序列化；本轮没有新增线路协议或把 JSON 回调称为完整业务 owner。

`calibration_request()` / `screen_runtime_calibrate()` 提供本地调用同一个执行器的入口；没有独立的新网络命令，也不宣告尚未实现的协议能力。

| 阶段 | 原厂动作 |
|---|---|
| 1、2 | 读取状态及 age；CO₂ age 必须 >1597，TVOC 必须 >3195；0x52 拒绝，TVOC 还拒绝 0x56。进入采样或报告失败 |
| 3 | 每 120 次 poll 保存一个读数，共 10 个；次数为任务轮询，不直接写成秒数 |
| 5、7 | 排序，极差 >=201 拒绝；<=200 才发校准命令 |
| 8 | 报告 2=未发出/失败，3=命令已发出；3 不能视为传感器确认 |
| 9、16 | 等待 22 次 poll，再清请求位、恢复状态并回到阶段 1 |

命令：

- CO₂ UART1：`11 03 03 01 90 58`，基准值 400（大端）；本实现没有新增任意 ppm 设置接口。
- TVOC UART2：`11 02 03 00 EA`。

`calibration_emit` 回调返回 true 才表示 UART owner 接受命令。返回 false 则报告失败，不冒充已发出；没有回调时不推进执行器。调用方必须按原厂任务节奏驱动 poll，并提供实际 age、读数及状态。初始状态设为 0x52，避免没有有效传感器状态就开始校准。

按原厂保留校准状态槽，但与显示指标状态隔离：CO₂ 执行器竟使用 `aa8+7`，而快照把它作为 PM2.5 状态输出；不应因此覆盖社区 PM2.5 的真实性。原厂报告 3 是发命令后直接设置，未等待经过验证的传感器校准完成应答。

原厂缺陷与替换行为：

- 重复请求已激活通道时，会跳过 client_token 查找并使用空指针。CPU 对照复现该路径；替换实现安全拒绝，保持原请求。
- 原厂样本缓存没有下标保护；替换实现对损坏下标拒绝继续写入。
- `hcho_install` 仅校验 token 后 ACK，没有传感器校准操作。保留这一行为；不新增不存在的甲醛校准命令。

## 验证与剩余接入

独立分析目录保留原始镜像、Unicorn 2.1.4 脚本和完整结果。仅替换 I²C 读取；温湿度计算、CRC、浮点辅助和 pow 都执行原厂机器码。校准仅替换 UART 输出及快照/报告出口。服务处理器另替换 cJSON 查询和时间，验证的是解析后的业务语义，不是 JSON 语法。

- 223 组温湿度输入：所有定点输出、计数及 double 状态与原厂**逐值完全一致**。
- 180 组校准单步和 3 条完整双通道流程：内存状态、命令、快照和结果报告顺序一致。
- 30 组解析后校准服务输入：正常请求位/应答行为一致；其中 9 条原厂空指针路径改为安全拒绝。
- 已导出不含原厂代码的 CPU 输出 fixture 到 tests/，普通 CTest 不依赖私有固件或 Unicorn。
- 补充 CRC 失败不变性、HCHO 越界/截断、无回调/发送失败、runtime 显示模型接入测试。

尚需 BSP 读实际配置和样本、提供传感器 UART owner，并把 UART JSON 解码/应答绑定到这些 runtime 接口。校准准确度、实际节奏、发命令后物理变化仍需实机验收。这里没有访问大金网络服务；未来网络入口统一走 iotcloud。
